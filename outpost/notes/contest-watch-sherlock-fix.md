# 一次「两条腿都断了」的修复：为什么一个监控源长期显示"未知"

## 症状

一个竞赛监控脚本有 4 个数据源。汇总行长期是这样的：

```
live: imm=none  cantina=none  c4=none  sherlock=?
```

`?` 表示"未知"，而它**一直**是 `?`。当时的第一反应是"网络不通"。

## 排查

**猜测 1（错的）**：UA 被拦。
实测：从同一台机器直接请求 `api.github.com`，配额 `59/60`、`orgs/<目标组织>/repos` 返回 `200`。**网络是通的，UA 不是原因。**

**真正的原因是两个 bug 叠在一起：**

1. **数据源 A（GitHub API）**：日志里写得很清楚 ——
   `HTTP Error 403: rate limit exceeded`。未认证配额（60/小时）被别的进程打满了。
2. **数据源 B（旧站点）**：已经 **404** —— 站点改版，那个页面不存在了。
3. **而且还有一个更深的 bug**：脚本里那个"是否存活"的字段（`*_live`）**只在出错分支被赋成 `None`，从来没有在任何地方被赋过真值**。

⇒ 也就是说：**即使上面两条腿都正常，它也永远显示"未知"。** 这个"未知"跟 403 无关，是代码从来不写这个字段。

## 修复

- 新增一条**直查新站点**的腿：解析页面里 Next.js 的转义 JSON，取状态字段
- 老站点/老接口保留为"发现新场次"用途，**但不再参与"是否存活"的判定**
- 汇总行加印原始状态，便于人工核对
- 备份原文件后再改

## 验证

```
live: imm=none  cantina=none  c4=none  sherlock=none  status=['FINISHED','success']
```

页面可见文字里写着 **"All 0 Active"** —— **独立佐证**：确实没有在开的场次。

## 残余风险（写清楚，不隐瞒）

`status` 里出现了 `success`，说明正则**会抓到非目标字段**。当前没有 `active/live/open` 所以安全，但**理论上可能假报"开着"**（是假警报，不是漏报）。要更稳需要逐个场次解析标题和时间。

## 这段过程里学到的一条

> **"取不到"和"没有"是两件事。**
> 把取不到静默当成"没有"，会让一个坏掉的监控看起来一切正常 —— 那是比报错更危险的状态。
